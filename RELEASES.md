# Релизы и клиники

## Как устроено

- **Один код** — этот репозиторий. Никаких веток «под клинику»: отличия между клиниками — это
  настройки клиники (в её базе) и, позже, включённые модули.
- **Каждая клиника — отдельный проект Vercel** (`clinics.json`) с двумя окружениями:
  - **Production** — боевая база Neon (`DATABASE_URL`);
  - **Preview (тест)** — отдельная тестовая база Neon (`STAGING_DATABASE_URL`), там клиника
    проверяет новую версию. На тестовой версии сверху жёлтая плашка «Тестовая версия».
- **Демо (`vethealio.vercel.app`)** — стенд разработчика: сюда новая версия выкатывается первой.
- **Автодеплой из git выключен** (`vercel.json`). Ничего не попадает к клиникам само —
  только командой `npm run clinic -- deploy`.
- **Миграции** (`prisma/migrations`) применяются автоматически при каждой сборке на Vercel
  (`vercel-build`): тестовая сборка мигрирует тестовую базу, боевая — боевую.

## Ветки и версии

- `develop` — текущая разработка.
- `main` — только выпущенные версии.
- Версия = git-тег `vX.Y.Z` на `main` (семантическое версионирование:
  X — несовместимые изменения, Y — новые функции, Z — исправления).
- Версия видна в приложении: Настройки → внизу, и на `/api/version`.

## Путь изменения до клиники

1. **Разработка** в `develop`. Изменение схемы БД — только через миграцию:
   `npm run db:new-migration -- <что_меняем>` (создаёт файл в `prisma/migrations` и применяет локально).
2. **Выпуск версии**: поднять `version` в `package.json`, дописать `CHANGELOG.md`,
   слить `develop` → `main`, поставить тег `vX.Y.Z`, запушить ветку и тег.
3. **Проверка разработчиком** на демо: `npm run clinic -- deploy demo vX.Y.Z --prod`.
4. **Проверка клиникой** на её тестовой версии со своими тестовыми данными:
   `npm run clinic -- deploy <клиника> vX.Y.Z` → ссылка для клиники.
5. **Прод клиники**, когда она подтвердила: `npm run clinic -- deploy <клиника> vX.Y.Z --prod`.
   Собирается **тот же тег**, что клиника проверяла.

Срочное исправление: ветка от тега (`git switch -c hotfix/x vX.Y.Z`), фикс, тег `vX.Y.Z+1`,
выкатка как выше, затем слить фикс обратно в `develop`.

## Команды

```bash
npm run clinic -- status                              # кто на какой версии
npm run clinic -- deploy veteridaria v0.3.0           # тест клиники
npm run clinic -- deploy veteridaria v0.3.0 --prod    # прод клиники
npm run clinic -- deploy all v0.3.0 --prod            # все клиники (кроме демо)
npm run clinic -- new <slug> "<Название>" <email>     # новая клиника целиком
npm run clinic -- catalog all --dry-run              # что добавит стандартный каталог услуг
npm run clinic -- catalog all                        # добавить недостающие услуги (свои не трогает)
```

`new` создаёт проект Vercel, секреты, две базы Neon (боевую и тестовую), применяет миграции,
заводит админа с паролем (одинаковым для теста и прода) и пишет доступы в `clinics.local.md`
(файл не коммитится).

## Правила для миграций

- Не удалять и не переименовывать колонки за один шаг: сначала добавить новую, перенести
  данные, и только в следующей версии удалить старую. Тогда клиники на разных версиях
  не ломаются.
- Никогда не править уже выпущенный файл миграции — только новый.

## Модули и лицензии

- Модули описаны в `lib/modules.ts`. Сейчас лицензируемые: `inventory`, `staff`; запланированы
  `smsReminders`, `presvet`, `knowledgeBase`.
- Без лицензии клиника получает модули по умолчанию (сейчас склад и персонал).
- Лицензия — ключ, подписанный закрытым ключом `~/.vethealio/license-private.pem`
  (**хранить в надёжном месте и сделать резервную копию**; без него новые лицензии не выпустить).
  В приложении только открытый ключ, поэтому клиника не может включить модуль сама.
- Выдать лицензию облачной клинике (пишется в её боевую и тестовую базы, без передеплоя):
  `npm run clinic -- license veteridaria inventory,staff,presvet --expires 2027-12-31`
- Вернуть модули по умолчанию: `npm run clinic -- license veteridaria default`
- Локальная установка: `node scripts/license.mjs <клиника> <модули>` → отправить ключ клинике,
  она вставляет его в Настройки → Модули → «Ввести лицензионный ключ».
